# Frontend Step 7 Report: Checkout + Razorpay Payment

## 1. Step Summary
Successfully integrated the complete customer checkout flow with Razorpay.
This included dynamically dispatching actual backend orders (`POST /api/v1/orders`), initializing Razorpay dynamically via the loaded script without any frontend secrets, and passing the Razorpay payment response firmly back to the backend for definitive signature validation (`POST /api/v1/payments/razorpay/verify`). The frontend safely blocks multiple instantiations, protects against client financial tampering, correctly navigates to the success page upon server verification, and leaves cart-clearing exclusively to the backend.

## 2. Backend APIs Inspected
- `POST /api/v1/orders` (Order Creation)
- `GET /api/v1/orders/:orderId` (Fetching success details)
- `POST /api/v1/payments/razorpay/verify` (Razorpay Signature Validation)

## 3. Order API Contract
Documented in `PAYMENT_CHECKOUT_API_CONTRACT.md`. We transmit ONLY the `addressId` and optional `couponCode`. The backend fully asserts subtotal, shipping, discount, and grand total independently without trusting client values.

## 4. Payment API Contract
Documented in `PAYMENT_CHECKOUT_API_CONTRACT.md`. The frontend only forwards the three fields generated by the Razorpay UI handler (`razorpay_order_id`, `razorpay_payment_id`, `razorpay_signature`) to the backend. The backend `RAZORPAY_KEY_SECRET` asserts its validity.

## 5. Razorpay Integration Architecture
A utility `frontend/src/utils/razorpay.js` dynamically inserts `https://checkout.razorpay.com/v1/checkout.js` on-demand into the DOM (resolving only once) protecting the UI against multiple inclusions and keeping the initial bundle lean. The initialization exclusively utilizes the `keyId` supplied by the authenticated `/orders` response.

## 8. Checkout State Architecture
The `checkoutSlice` centralizes the lifecycle: `orderCreationLoading`, `paymentStatus` ('idle' | 'initializing' | 'open' | 'verifying' | 'success' | 'failed'), and `successOrderId`. It avoids duplicating Cartesian constraints from other slices (shipping, cart).

## 9. Order Creation Flow
When the user clicks "Continue to Payment":
1. Triggers `POST /api/v1/orders`.
2. Blocks UI inputs.
3. Upon success, captures `amountPaise`, `currency`, `keyId`, and `razorpayOrderId`.

## 10. Razorpay Flow
Uses the captured variables to initialize `new window.Razorpay(options)`. Safely catches closure via the `modal.ondismiss` hook to gracefully reset payment status.

## 11. Signature Verification
The success `handler` immediately dispatches the payload to `/api/v1/payments/razorpay/verify`. A spinner reflects this critical "Verifying..." transition state.

## 12. Payment Failure Behavior
Failure events (either network or Razorpay UI) route safely through Redux into user-facing Toasts. The `paymentStatus` restores back to 'failed' enabling easy manual "Try Again" retries.

## 13. Retry Behavior
Retry hits the exact same Checkout Flow securely because if an order was "started" but interrupted, a fresh backend invocation ensures correct server state replication or leverages backend idempotency. 

## 14. Idempotency
Double-click prevention is heavily enforced locally via state toggles (`isCheckoutDisabled` flag). Backend verification explicitly guards against verifying duplicate orders implicitly.

## 15. Cart Behavior
Cart is deliberately **not** reset by the frontend. The `verifyPayment` API natively deletes items inside its atomic transaction. The front-end implicitly reflects this via standard navigation to the new page.

## 16. Success Page
Created `/order-success/:orderId`. It queries `/api/v1/orders/:orderId` to display the actual paid amount securely, blocking guest leaks.

## 17. Authentication
